# ChengziCV Case Factory

> **套件启动**：开始任何工作前，先读取并执行 `../chengzicv/references/suite-bootstrap.md`（共享工作区、档案恢复、产物落盘、事实边界）。

> latest：技术案例按目标职级设计，保留功能范围、实现关系和版本演进。完整项目使用背景、我的职责、成果三段式，标题先说明工作内容，内部变量和状态常量用准确中文含义表达，机制与技术栈保留。深度规则为本版独立快照，不修改历史版本。

默认产品是**虚拟简历＋岗位入门**。让读者既看懂工作在做什么、是否愿意继续了解，也看见相关经历怎样呈现出思考与执行深度。不是把一串职责换成简历，也不是默认发一套训练营材料。

## 默认交付

每岗交两份可直接展示的 Markdown：

- `01-岗位标杆虚拟简历.md`：小橙的教育、重点工作或实习、与岗位匹配的第二段深度经历、相关技能；重点经历写清背景、个人职责和成果，按内容展示工作范围、实现、取舍与验证，不逐条套固定流程。
- `03-岗位入门.md`：从具体任务和材料开场，以故事串联行业、工具、协作、判断、工作感受、相近岗位区别和入门选择。

沿用既有文件名，不为编号重建重复文件。用户明确只要其中一份时按指定范围交付；不能因旧版规则默认漏掉虚拟简历。作品集、面试手册、CSV、完整 PRD、README和验收报告仅在明确需要时追加。

两份材料使用同一个小橙，姓名、公司、身份、时间、职责、数字和项目进展一致。品牌“橙子 CV”和其他真实人物姓名不变。案例性质按 `references/product-boundary.md` 统一披露一次，展示正文不重复加免责声明、内部状态或制作旁白。真实个人简历转交 `chengzicv-resume`；本 Skill 的身份、公司、职责和数字不得进入真人事实台账或冲高确认台账。

## 使用顺序

1. 读取 `references/product-boundary.md`、`references/user-case-pack.md`、`references/experience-depth.md` 和 `references/benchmark-resume-standard.md`。用户想先看"什么简历能过什么厂"的真实标尺、或要按真实 offer 案例对照差距时，再读 `references/real-offer-benchmarks.md`（脱敏真实案例，与小橙虚拟标杆严格隔离，不改编不进小橙简历）。
2. 技术/后端/AI 工程案例读取 `references/technical-evidence.md` 校准机制、标题、演进与证据。其他岗位读取 `references/gold-standard.md` 的相应范文。已有同岗位确认稿优先，技术案例不必加载整套供应链范文。
3. 按 `references/production-contract.md` 研究公开 JD 与必要的官方资料；批量时再读 `references/batch-planning.md`。
3.5. 专业深浅有争议时读 `references/depth-calibration.md`，按目标职级和真实 JD 校准。跨模块实现可以属于本人职责，不将工程实现自动删去或改写成产品决策。
4. 先记录用户指定的经历数量、必含方向、格式和篇幅，再按项目不同的技术重点建立共享事实，成稿读取 `references/signal-writing.md`，用信息排序、短链路和新旧对比写紧凑的 Markdown 简历，不改为 HTML/PDF。再写两份材料；完成后按 `references/quality-gates.md` 检查。
5. 批次进度用 `references/manifest-schema.md`；单岗修改不为脚本额外创建清单。

## 经历要有深度

- **S/T**：谁有需求、遇到什么问题、目标和约束是什么、小橙负责哪部分。
- **A**：拿什么材料，怎样拆解与判断，为什么选这个方案，如何协作推进。方法体现在动作中，不堆术语；审批、质量判断、客户承诺仍由对应角色负责。
- **R＋复盘**：交代实际结果，也保留延期、追加成本、未售库存等代价；回到记录解释问题，写清后续调整及仍待观察的效果。
- **技术深度与验证**：功能范围、实现机制、演进取舍和交付验证共同呈现，不要求每条都有故障与提升。已有版本演进保留前后原因，虚拟构造时按业务需要设计，不强制每个项目安排失败故事。数字用于解释判断，且能重算。
- 第二段经历先服从岗位匹配。业务、运营等岗位可用有自主责任的小型经营或服务项目，体现需求验证、投入约束、执行交付与复盘；科研和技术岗优先用持续性的专业课题、实验室研究或工程项目，呈现研究问题、控制条件、证据链、方案取舍、重复验证和结论边界。
- 创业经历不是默认必选项。不能只把课程设计改名为创业，也不靠“CEO”、巨额营收或漂亮增长数字增加深度。需执业资格、实验设施或特殊安全条件的岗位，不为了加入自主项目而编造独立服务、收费或越权实践。
- 深入的课程或研究项目可以保留，但不能只有作业步骤、软件清单和汇报结论；需要写出为什么这样设计、证据如何改变判断、为什么舍弃另一方案，以及结果还不能证明什么。
- 范文决定具体程度，不提供跨岗换皮模板；不强制三版方案、反转、争吵、一次 AI 错误或固定成功结局。

## 岗位文章写法

用任务和材料开场，角色对话只交代事情。保留少量可观察的记录和一个轻量判断，解释为什么处理、用什么处理、交给谁。工具随工作需要出现，不逐项塞入飞书、AI和开会。

短小具体的小标题帮助浏览；术语随任务解释。工作感受、相近岗位比较和入门建议回到前面的动作，不根据性格标签或一次练习判定适配。说明同名职位也可能有不同职责。文章以讲清楚为准，不固定字数、标题数量，也不扩成完整操作手册。

公开事实就近附来源；人物、对话、经营和工作数字在内部标为情境设定，不冒充真实采访、研究或业绩。跨多日写清跨度，计划不写成完成，前后变化不当作因果证明。

## 展示与协作

简历正文不使用中英文单引号或双引号，包括强调词、状态名和转述内容；改为直接陈述，不能换成其他引号变体。允许用 → 表示真实顺序，用顿号列举并列项，技术栈允许用 / 分隔。箭头不能把并发或分支关系误写为顺序，改标点不删事实。

展示稿不出现“没有后台”“没有上线”“没有改口就不要编”“请替换数字”“不能直接投递”“不保证 offer”等制作旁白，不输出 Manifest、CASE-ID或证据状态码。业务约束、数字口径和进展限制仍要讲清。

首次调用用一句话说明交付后开始，不背诵介绍，不要求用户再次提供已有岗位、素材或确认稿。批次默认先建目录与计划，**一次完成一岗的两份材料，用户 check 通过再进入下一岗**；用户已明确授权连续生产时按其要求。自查完成不等于用户认可，修改意见先落实到当前岗。

局部修改保留用户内容；大幅重做另存版本，明确当前审核稿。交付两份 MD 链接和简短说明，不额外给生产报告。仅在用户明确要求时外部发布。旧批次只做兼容，不恢复成默认四件套。
