## 项目经历

### 交易下单改造｜超时隔离与库存预占冲突

2023.03—2024.12｜技术负责人、核心开发

**项目背景**：平台下单需完成价格核验、优惠校验及库存预占。促销时库存接口长尾上升，原共享线程池被占满，连带拖慢普通订单；客户端重试与库存取消还会交错到达，导致订单状态迟迟无法确定。

**我的职责**：负责订单服务和跨服务协议，带领小组完成接入；库存团队实现预占记录与库存变更。

- **下单超时与线程隔离**：从线程栈与排队指标定位请求已超时、队列仍在补做库存调用。按促销与普通库存路由拆分线程池，各设有界队列，入口生成截止时间，任务出队先检查剩余预算，再设置远程调用超时；排队超时直接拒绝；线程池饱和时，不让下单线程代为执行库存调用。已发出的超时请求进入查单确认，不把本地取消当作远端撤销。
- **库存预占与取消冲突**：以订单号关联库存预占记录，统一处理预占、确认和取消三种状态。取消先到时写取消记录，迟到的预占不能再扣库存；同一订单的重复请求返回已有结果。库存数量与预占记录在同一事务中修改，以唯一键和条件更新裁决预占、确认、取消竞争，尚未扣减库存的订单取消时不执行库存返还。
- **订单状态与事件原子提交**：订单携带版本号，支付与关单按旧状态条件更新；先请求支付侧关闭支付单，再推进本地关单；支付侧已支付则转支付完成，状态不明进入查单补偿。订单状态和事件在同一 MySQL 事务提交，投递器按事件编号重发，消费方将去重记录与业务更新同事务落库。

**成果**：完成 6 个商家灰度并推广至全量。相同 8×8 核应用资源、相同数据集与模拟下游依赖下，以 800 请求/秒回放 30 分钟，下单 P99 从 920 ms 降至 310 ms；向促销库存路由注入 5% 的 2 秒延迟时，普通订单技术成功率从 96.7% 升至 99.8%。补齐取消先到、重复预占及超时后远端成功的故障用例，异常订单可按原订单号查询并确认最终状态。

### 商家订单检索｜增量同步与稳定翻页

2020.08—2022.05｜核心开发

**项目背景**：约 1.1 亿条历史订单，商家按状态、时间、收货地区组合筛选。原 MySQL 查询需要多组索引，深分页越翻越慢，新增订单又会使跨页结果重复。本人负责将商家筛选迁至 Elasticsearch，交易操作仍回主库核验。

**我的职责**：实现查询索引、增量同步、历史回填和游标分页。

- **订单查询索引设计**：以租户＋订单号唯一标识索引记录，将筛选和列表展示需要的字段展开后写入同一索引记录，避免逐单回查；检索固定带租户过滤，详情和修改重新校验归属与 MySQL 当前状态。将下单时的商品信息与订单一起写入索引，避免商品改名改变历史订单。
- **回填与增量并行**：先记录数据库变更日志的同步起点并持续接收增量变更，再分批读取主库历史数据回填索引；索引所需字段变化时同步递增订单版本，索引只接受更新版本的数据，旧回填不能覆盖新事件。删除同步为带版本的软删除文档并在查询中过滤，避免延迟事件将已删除订单重新写活。
- **订单列表稳定翻页**：2021 年升级后固定每轮查询的数据快照，按创建时间和支持排序的唯一订单键排序。翻页凭据同时记录本轮筛选条件的标识、上一页末条记录的排序值和查询快照编号，继续读取后续结果，避免新订单插入造成跨页重复。不再支持任意跳页，筛选条件变化重新建视图，查询快照到期提示刷新；导出复用同一分页读取器，逐批写文件，避免每次翻页都从头扫描并跳过前面的记录。

**成果**：在同一订单快照、50 并发及 20 组筛选条件下，每页 50 条、连续翻至第 100 页时的单页查询 P95 从 3.4 s 降至 180 ms。完成历史回填与字段级抽样校验，连续 7 天观测增量索引延迟 P99 为 2.6 秒；用户可按订单号直查主库确认新订单，商家筛选接受短暂延迟。

### 线上排障助手｜可恢复 Agent 执行与证据定位

2025.05—2026.08｜后端负责人、调度内核开发

**项目背景**：值班排查需要在日志、链路和发布记录之间切换。早期检索后直接总结经常拿旧发布记录解释新故障，工具失败后又重复查询。项目面向内部值班人员生成带证据的排查建议，生产变更仍由人执行。

**我的职责**：设计 Java 执行内核和只读工具网关，与运维同事维护诊断规则，用 Python 构建离线回放评测。

- **任务规划与工具调度**：模型输出结构化任务和依赖，调度器只并行执行依赖已满足的节点；限制单任务最多 4 个工具并发、12 轮模型调用、120 秒总时长。遇到接口限流时，在剩余时间内延后重试，耗尽后带已有证据结束，不无限重试。
- **任务恢复与结果复用**：按任务编号和步骤编号保存计划版本、工具参数、结果引用与状态，计划修订生成新步骤标识；进程恢复后跳过已完成节点，只重跑中断的只读调用。日志查询固定绝对时间窗，结果复用同时匹配参数、数据源、权限范围与有效期，避免同一句问题复用过期现场。
- **证据时间窗与上下文选择**：日志片段保留调用链标识、时间范围和来源，发布记录按故障时间对齐；先按服务与时间筛选，再挑错误样本和相关调用链。大结果写对象存储，模型只接收摘要、证据编号和必要片段，超出预算按证据优先级裁剪，摘要不覆盖原始记录。
- **工具权限与回放评测**：网关逐次校验操作者权限，仅开放参数受限的查询接口，不提供任意 SQL、Shell 或生产写操作。固定 80 个脱敏历史案例作为回归集，按首次错误步骤区分计划错误、工具参数错误和证据误读，将失败样本回放到相同模型版本与工具快照。

**成果**：在上述 80 例上，使用同一人工判定标准，结论正确且引用有效的案例从 46 例增至 65 例；按同一案例内无新增现场信息判定重复调用，80 例合计由 500 次降至 310 次（下降 38%）。内部 12 人试用，交付带证据的排查报告、执行轨迹及失败分类；跨服务证据不足时保留未决项，不自动执行修复。
