# 技术与岗位备答卡

仅在用户明确要静态题目、参考回答、考察点和递进追问时读取。用户要现场训练时转连续问答，不一次泄露整套参考答案。

## 题目如何选

从 JD 的关键任务与技能出发，找到简历中的具体动作或实现，问两者之间真正需要验证的内容。没有 JD 时，以用户目标和已知项目为依据，不宣称覆盖岗位所有要求。

通常选择 8—10 题，但用户指定数量优先，材料不足不硬凑。重点落在个人贡献、选型原因、实现流程、异常处理、验证方式、边界和结果口径。不能仅因简历出现一个工具就假设已掌握其高级能力。

岗位要求但简历没有证据的内容可以单独列“知识/情景准备”，不把它写成项目经历。

## 先给完整答案，再放题目讲解

默认先连续交付全部题目的“问题、完整口语回答、递进追问”，让用户可以一口气学习或朗读。然后在末尾按题号集中写“为什么会问、考察点、需确认的事实”。不在每道回答之间插入长解析。用户明确指定每题一张卡且讲解紧随答案时，才按其格式调整。

每题准备这些内容，但按上述顺序呈现：

1. **面试官可能问**：口语化、有明确范围的问题。
2. **你可以这样回答**：先答重点，再按已确认事实展开。没有实操证据时写成知识理解或未来方案，并保留真实边界。
3. **为什么会问**：简短说明该题关联哪条岗位要求和哪处简历事实，不夸称企业实际评分表。
4. **考察点**：一到两个核心能力，避免长列表。
5. **递进追问**：一到两个关于操作细节、异常、取舍或验证的问题。基于答案中实际可深入的内容，不加入未提到的技术实践。
6. **需确认的事实**：仅在确有缺口时列具体问题；与口述回答隔开。

不要在个人回答里补写工具版本、流量规模、生产事故、压测结果、上线机制或代码行为。公共技术资料只能支持知识解释，不能证明候选人使用过。

题目、回答和追问用普通正文、标题与加粗，不使用引用块、代码块或长表格。用户明确只要问答时不额外输出题目解析。

用户明确要追问参考答案时提供；否则追问用于练习即可，避免每题扩张成一篇教材。不确定的技术机制和版本信息使用官方文档、论文或实际代码核验；无法核验则说明不确定，不编造结论。
