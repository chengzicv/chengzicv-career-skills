# 招聘岗位的人才市场映射

仅在目标岗位是招聘、猎头、TA、人才寻访或招聘项目 Owner 时读取。

## 目标链路

每一类重点人才至少形成以下闭环：

```text
目标业务/产品线
→ 岗位族与实际任务
→ 竞品公司及对应业务线/产品
→ 可检索的岗位与技术关键词
→ 简历中应出现的能力证据
→ 候选人可能顾虑
→ 可验证的项目吸引点
```

只列“网易、字节、米哈游”等公司名不算完成。必须说明为什么该公司的哪条业务线会产生相近人才，以及用什么关键词能找到。

## 研究表字段

| 字段 | 要回答的问题 |
| --- | --- |
| 目标团队/产品 | 在做什么类型的产品或交付 |
| 岗位族 | 客户端、服务端、引擎、测试、策划、美术、数据、产品、项目、运维等 |
| 关键任务 | 这个岗位实际解决什么问题 |
| 竞品公司 | 哪些公司可能拥有相近人才 |
| 对应业务线/产品 | 具体到工作室、产品线、游戏/应用、平台或技术团队 |
| 搜索关键词 | 职位同义词、产品类型、引擎/语言/工具、平台、方法和交付词 |
| 能力证据 | 简历上什么行为、规模、质量、结果或作品能证明匹配 |
| 顾虑 | 薪酬、地点、项目阶段、技术方向、稳定性、成长、流程速度等 |
| 吸引点 | 目标项目已公开且能验证的工作内容、挑战、平台或发展空间 |
| 证据等级 | 已核实事实 / 招聘推断 / 待内部确认 |

一个公司包含多个业务线时分行记录，不能把公司品牌当作统一人才池。

## 岗位关键词扩展

同时扩展四类词：

1. **职位同义词**：例如后端/服务端、TA/技术美术、SRE/运维开发；
2. **业务词**：产品品类、玩法、平台、用户场景、商业或交付模式；
3. **技术与工具词**：语言、引擎、框架、数据栈、制作工具、测试或部署方法；
4. **证据词**：上线、性能、稳定性、并发、留存、版本、资产、流水线、跨团队、交付等。

先用较宽组合找市场，再根据简历噪声调整。不要把一个过窄布尔串写成所有渠道通用标准答案。

## 学校与专业

学校、专业、实验室、赛事和社区只能用于扩展校招、实习生或初级人才的触达渠道。研究时可以记录计算机、软件、数学、统计、数字媒体、动画、美术、交互、工业设计等与岗位相关的专业方向，但必须继续检查项目、作品、实习和实际能力。

禁止：

- 用学校层次直接代替能力判断；
- 因非对口专业自动排除有真实作品和能力证据的人；
- 推断或使用性别、年龄、籍贯、婚育、健康、民族、宗教或政治倾向进行筛选。

## 能力画像

能力画像写成可观察证据，不写“沟通好、抗压强、学习快”这种无法筛选的评价。

优先覆盖：

- 做过什么对象、规模和阶段；
- 本人负责哪一段，如何与上下游协作；
- 使用什么工具或方法解决什么约束；
- 交付物、质量、效率、稳定性或业务结果如何验证；
- 遇到冲突、延期、需求变化或失败时怎样处理。

## 候选人吸引话术

先判断候选人最可能关心什么，再从已核实信息中选择两三点，不要一次倒完所有卖点。

推荐结构：

```text
为什么联系你：引用候选人的具体经历
岗位为什么相关：说明目标任务与其证据的连接
现在值得聊什么：给一两个可验证的项目或能力挑战
仍需确认什么：对薪酬、汇报线、项目阶段等不确定项保持透明
下一步：给低压力、明确的沟通入口
```

不得承诺未确认的薪资、职级、Offer、HC、项目归属、晋升、长期稳定或保密项目内容。

## 对招聘工作的价值

人才地图最终要转成执行动作：

- 和用人经理确认画像时，能指出哪些条件决定人才池大小；
- 选渠道时，知道去哪个业务圈层找什么人；
- 搜索时，拥有公司、业务线、岗位和技术多组关键词；
- 初筛时，检查行为证据而不是品牌光环；
- 沟通时，按候选人顾虑选择真实卖点；
- 复盘时，能把回复率、推荐率、面试通过和 Offer 流失落回画像、渠道或话术问题。
