# 事实模块库与按岗位排序

同一位候选人要投很多岗位时，不要每次整段重新生成招呼语。先把已确认事实拆成模块，每个模块一句话、口径固定，再按岗位侧重换顺序。模型只负责两件事：选派别和排顺序，以及写开头约 15 个字；事实句子从模块库里原样取，不临时改口径。

## 1. 什么时候用

- 同一方向要投 3 个以上岗位，或用户说“以后我自己拼”“给我一套能反复用的话术”。
- 用户已经有一版自己满意的手写话术，希望保留语气、只换重点。
- 单个 JD 只要一条话术时，可以不建库，直接按 `methodology.md` 写。

## 2. 怎么拆模块

从简历和档案的已确认事实里，按“对方会用它判断什么”拆，常见 5—7 个：

| 模块 | 回答招聘者的哪个问题 | 写法 |
| --- | --- | --- |
| 身份 / 产品 | 你是谁、做成过什么 | 头衔或角色 + 一个可核实的规模数字 |
| 核心岗位动作 | 能不能接住这份工作 | 现任岗位 + 负责对象 + 一个前后对比 |
| 交付 | 多快能出东西 | 交付物 + 周期 + 上线后的一个结果 |
| 增长 / 业务结果 | 做的东西有没有用 | 只写本人负责部分的结果，团队结果不写成个人成果 |
| 跨职能 | 能不能和业务方、客户沟通 | 相关经历 + 可迁移动作 |
| 背书 | 凭什么相信你 | 投资、名次、证书、头衔，每个都要有出处 |
| 选用模块 | 只对少数岗位有用 | 例如成交、外语、行业资质，默认不放 |

每个模块写成一行表格：模块名、句子、证据出处。证据出处必须指向简历、作品、截图或用户在对话里的明确确认。写不出出处的句子不进库。

另配一句固定结尾，见 `methodology.md` 第 5 节的“结尾的两种写法”。

## 3. 按岗位换顺序

先看 JD 最看重哪类能力，再决定哪个模块打头。打头模块的开头约 15 个字就是 BOSS 预览区，必须单独成立。

| 岗位侧重 | 模块顺序（示意） | 打头写什么 |
| --- | --- | --- |
| 通用 | 身份 → 核心动作 → 跨职能 → 背书 → 结尾 | 角色 + 规模数字 |
| 提效、数字化、内部工具 | 核心动作 → 交付 → 身份 → 背书 → 结尾 | 现任岗位 + 负责对象 |
| 增长、裂变、渠道 | 身份 → 增长结果 → 核心动作 → 结尾 | 规模数字 + 增长来源 |
| 售前、解决方案、客户成功 | 背书（表达类）→ 跨职能 → 核心动作 → 结尾 | 名次或客户场景 |
| 业务方是销售、运营或卖货团队 | 交付 → 核心动作 → 选用模块 → 结尾 | 交付周期 + 业务结果 |

顺序表是起点，不是死规则：岗位层级明显低于候选人时，仍按 `methodology.md` 第 4 节先降层级信号，再排序。

## 4. 拼完检查五项

1. 开头只放一个模块，身份加一个数字，不要把两个模块的数字挤在一起。
2. 每个数字和简历同一口径；简历里带“约”的保留“约”。
3. 同一条消息里数字格式统一：千分位、单位、中英文之间的空格。
4. 括号里只放补充说明，不放会影响判断的信息，例如“已交接”“团队成果”。
5. 全篇一种语气。书面就书面到底，不在结尾突然换成“哦~”“呀”。

## 5. 存放位置

模块库属于候选人事实，按套件启动契约写进 `{工作区}/output/`，文件名 `YYYY-MM-DD-姓名-话术模块库.md`，并在档案材料索引里登记。它是供候选人反复拼装的中间产物，保留 Markdown，不必渲染 HTML。事实有变化时先改简历和档案，再改模块库，不在模块库里单独改口径。
