# 最终审查

## 访谈完整性

- 补强过程中是否始终一次一题？
- 每题是否显示进度、选项、跳过入口和同岗位参考案例？
- 是否把案例与用户事实严格隔离？
- 用户选择区间、量级或定性结果时，最终表述是否保持相同颗粒度？
- 用户跳过后是否停止追该缺口？
- 最终 bullet 与 STAR 讲法是否只使用用户原文、选择或主动补充？

交付前必须审查。不要因为句子顺就默认可用。

## 审查清单

### 真实性

- 有没有新增用户没说过的公司、学校、学历、证书？
- 有没有新增用户没说过的技术栈？
- 有没有把 JD 关键词硬塞成用户经历？
- 有没有把顾问建议写成事实？
- 有没有没口径的数据？

### 动词强度

- “负责”是否有证据？
- “主导”是否有证据？
- “搭建体系”是否真的有体系？
- “0-1”是否真的从无到有？
- 应届生是否用了过强的管理者动词？

### 技术可信

- 技术名词是否来自原文或用户确认？
- 每个技术栈是否能对应到动作？
- 有没有学生项目写成企业级高并发？
- 有没有只堆技术名词不讲业务对象？
- 有没有 HR 完全看不懂的技术黑话小标题？

### 结构与可扫描性

- 工作、实习、项目和校园经历中的每条职责 bullet 是否都使用 `- **小标题**：正文`？
- 小标题是否指向具体业务对象、功能模块、问题类型或结果，而不是“核心能力”“系统优化”等空标签？
- 是否出现为了可读性删掉材料中可辩护的关键实现细节？
- 是否使用小标题分区并用完整句子承载细节，而不是连续堆叠 `/`、`+`、`→`？
- 任一经历职责 bullet 缺少小标题时，本次审计不通过，返回局部重写后再交付。

### 去 AI 味

- 有没有赋能、闭环、全链路、端到端、显著提升？
- 有没有“能力强、思维好、经验丰富、扎实”？
- 有没有每个人都能用的空话？
- 有没有工具、动作、流程、结果？

### 匹配度

- 期望岗位是否明确？
- 个人优势是否和 JD 对齐？
- 最强经历是否前置？
- 技能顺序是否和目标岗位相关？
- 无关经历是否压缩？

### 企业敢招风险

- 对学生、初级、转岗或中小企业岗位，简历是否只证明“厉害”，没有证明“能接住这类活”？
- 是否把课程项目、练习项目写成大厂架构或高层级经验？
- 是否让招聘方担心薪资、稳定性、岗位意向或长期匹配？
- 是否补了可验证交付物：作品集、Demo、测试账号、接口文档、部署说明、工程图、BOM、SOP、台账、复盘表？
- 如果交付物不存在，是否明确标成“建议补充”，而不是写成已完成事实？

### 能力证据覆盖与可辩护性

- 每条强 bullet（有数字、有强动词、有独特卖点）是否都有对应岗位能力证据卡？
- 每张卡是否标明至少一项通用能力维度，并按目标岗位补充岗位专业能力？
- 每张卡是否只引用“已确认”事实？
- 卡片标题是否使用“能力维度｜岗位专业能力｜对应经历”，而不是内部编号？
- 追问预演有没有跑：每张卡的 3 个模拟追问，台账里能不能答上来？
- 预演失败的 bullet 是否已经降级或重写，而不是只删卡？

### 双读者校验

读取 `dual-reader-rewrite.md`，两份 checklist 双跑：

- HR 初筛视角：身份标签、意向对齐、硬关键词位置、前 2 条 bullet 对齐 JD、小标题可扫描、数字前置。
- 业务负责人视角：场景→判断→动作→结果结构、hook 细节、可验证交付物露出、技术细节与阅读负荷平衡。

### 受众隔离

对外发简历和作品集分别检查：

- 有没有 `[待确认]`、`需确认`、风险等级、事实/来源编号、顾问说明、使用提醒或练习要求？有就移到内部交付文档。
- 有没有“建议补充”“完成后启用”“不可投递”等内部状态？有就从外发文件删除对应内容，而不是删除提示后保留未证实主张。
- 简历是否只含候选人要给招聘方看的信息？作品集是否只含作品正文、案例、模板和必要的方法说明？
- 非实际业务案例是否以“方案案例/示例”在局部准确呈现，且没有被写成任职、客户、候选人或录用业绩？
- 内部培训文档是否只教准确解释事实和方法，没有教隐瞒、伪造或规避背调？

### 飞书项目手册与作品集

生成项目手册、作品集或飞书文档时，读取 `feishu-project-handbook.md` 并检查：

- 完整项目交付是否同时包含项目准备手册与面试官外发作品集两份独立文档？
- 两份文档是否共用同一事实型正文核心，并先给演示和项目全景，再进入局部实现与真实交付证据？
- 团队成果与候选人的个人职责是否已经自然分开？
- 每张核心截图是否紧邻解析，并能证明一个明确功能或交付物？
- 是否有 3—5 张真正解释系统、流程、职责或排障关系的图，而不是装饰图？
- 为帮助理解而补充的常见实现是否保持准备语境，没有变成候选人已完成事实？
- 准备手册的事实型正文是否清除了事实状态、顾问口径、使用说明和教学式标题，并采用可直接复制的候选人表达？
- “核验通过后可直接使用”的段落是否仍留在准备手册，且没有在未经核验时自动进入外发作品集？
- 外发作品集是否从事实台账独立生成，并清除“怎么使用、面试准备、模拟追问、建议补充、待确认”等内部语言？
- 两份飞书版本中的图片、视频和附件是否都为实际媒体块，而不是本地路径或占位符？
- 两份文档的权限、最终链接和所有权是否均已核验；应用代建时是否分别读取文件元数据确认目标 `owner_id`？

## 风险标记格式

```text
风险点：
- “主导XXX”偏强：原文只体现参与执行，建议改为“参与推进/承担XXX模块”。
- “提升50%”缺口径：建议补充原始数据，否则改为“缩短处理时间”。
- “熟练SQL”缺证据：经历里没有 SQL 使用场景，建议降级或补证据。
```

## 高风险词替换

| 高风险 | 替换 |
| --- | --- |
| 主导 | 参与推进 / 承担 / 负责其中的 |
| 牵头 | 协助推进 / 跟进 |
| 制定战略 | 参与方案讨论 / 整理执行计划 |
| 搭建体系 | 梳理流程 / 整理模板 / 建立台账 |
| 赋能 | 支持 / 帮助 / 用于 |
| 显著提升 | 如果无数据，改为改善 / 减少 / 支持 |
| 精通 | 熟悉 / 可使用 / 有一定基础 |

## 最终自检问题

交付前默问：

1. 用户拿这份简历去面试，能不能解释每句话？
2. 面试官追问“你具体怎么做的”，用户有没有话讲？
3. HR 30 秒扫简历，能不能看到匹配点？
4. 技术面试官看技术词，会不会觉得虚？
5. 哪些点必须提醒用户确认？
6. 每张岗位能力证据卡，用户能否在 30 秒内讲清能力结论、关键动作和结果？
