# 工作流

本文件规定完整简历顾问流程。不要跳过事实台账直接润色。

## 一句话策略

先把材料变成可追溯事实，再把 JD 变成能力模型，最后把事实按岗位需要重组为简历。

## 阶段 0：判断任务类型

先判断用户当前要你做什么：

| 用户意图 | 处理方式 |
| --- | --- |
| 给一堆材料，要完整简历 | 跑完整流程，先出稿再追问 |
| 给出简历、聊天、截图、PPT/PDF、视频等完整材料，要所有简历和对应作品集 | 跑完整流程；按岗位拆简历，并读取 `feishu-project-handbook.md` 同时生成项目准备手册与面试官外发作品集；需要飞书时分别完成发布与验收 |
| 已有简历，只想针对 JD 改一版 | 建轻量事实台账 + JD 模型 + 快速稿 |
| 只想优化某段经历 | 读模块规则，局部改写，输出 diff 和风险点 |
| 从零开始没有简历 | → 先触发阶段 0.5，再进入一次一问访谈 |
| 用户说"我没有经历"或"三无" | → 先触发阶段 0.5 的三无专用话术，再发经历雷达 |
| 想做职业规划再倒推简历 | 先问目标方向，再做 JD 模型和履历策略 |
| 想拿去交付客户 | 输出更完整，保留修改说明、追问清单、风险标记 |

从零访谈的规则：一次只问一个问题，等回答后顺着追问；用户说不出数字时引导量级而不编造；每挖完一件事当场转成 bullet 回读确认。

---

## 阶段 0.5：低阻力访谈契约（必读）

**触发条件：** 用户没给材料、第一次使用、说自己没有经历、需要从零访谈挖经历时。

**必须做的事：**

1. 读取 `references/low-resistance-onboarding.md`，按情景选对应话术输出
2. 发完开场话术后等用户主动提供材料，不要立刻提问

**追问前必须做的事：**

开始一段经历的补强前，输出 `low-resistance-onboarding.md` 的启动话术：
- 回显 2-4 条当前已有事实；
- 告知固定五步和可随时跳过；
- 下一条消息再单独输出第一张问题卡。

访谈进行中不要每题重复台账，只显示当前进度、一个问题、选项和一个同岗位案例。

**绝对不能做的事：**

- 在没有发过开场话术的情况下直接问经历
- 在一条消息里问两个或更多问题
- 每题不提供具体参考案例
- 把案例或选项中的细节写成用户事实
- 用"岗位证据地图"等内部术语对用户说话
- 用考试式问法（"你有没有销售经历？"）代替经历雷达

## 阶段 1：材料归档

用户可能一次塞很多材料，常见类型：

- 原版简历
- 修改版简历
- 目标岗位 JD
- 用户补充说明
- 用户自己反馈
- 你或其他顾问提过的修改建议
- 作品链接、项目说明、聊天记录

处理时先给材料编号：

```text
来源1 原版简历
来源2 第二版简历
来源3 目标岗位JD
来源4 用户补充信息
来源5 顾问建议
```

材料优先级默认：

1. 用户明确最新确认的信息
2. 修改版简历
3. 原版简历
4. 用户补充信息
5. 顾问建议
6. 你的合理推断

注意：顾问建议不是事实，只能作为改写方向，不能直接写成用户做过。

## 阶段 1.5：结构化解析

读取 `resume-schema.md`，把材料解析进标准简历数据结构。缺失字段标 `[待确认]`，不留空猜。后续所有改写都只动结构里的字段。

## 阶段 2：事实台账

读取 `fact-ledger.md`。

必须抽出：

- 已确认事实：可以直接写进简历。
- 待确认事实：可能有价值，但缺口径、缺数字、缺用户角色。
- 冲突事实：不同材料说法不一致。
- 禁用事实：明显夸张、无来源、背调风险高。

如果用户材料很乱，不要急着问一堆问题。先用现有事实写一版，再把关键缺口列出来。

## 阶段 3：JD 能力模型

读取 `jd-analysis.md`。

不要只提关键词，要拆出企业到底要解决什么问题：

- 这个岗位招来干什么？
- 第一关 HR 会搜哪些词？
- 业务负责人会看哪些证据？
- 用户现有经历里哪些能迁移？
- 哪些硬伤不能靠文字解决？

输出一段简历策略，控制在 5-8 条。

## 阶段 3.5：岗位风险画像与证据链

当用户是学生、应届、初级、转岗、学历不占优，或投递中小企业/传统行业/执行型岗位时，读取 `recruiter-risk-signals.md`。

不要只判断“用户会什么”，还要判断企业可能“不敢招”的原因：

- 会不会只做过同质化课程项目？
- 会不会太大厂导向，来了不稳定？
- 会不会只会软件/工具，不会交付？
- 会不会没有作品、文档、测试、部署、图纸、台账等可验证证据？
- 会不会岗位意向太散，让 HR 觉得不稳定？

输出策略时补一段“企业顾虑与证据链”：

```text
企业可能担心：
- ...

现有可用证据：
- ...

需要补的证据：
- ...
```

## 阶段 4：决定简历打法

简历不是平均展示所有经历。先定打法：

- 哪段经历放前面？
- 哪段经历压缩？
- 哪些技能前置？
- 个人优势写哪 3 个维度？
- 是否需要“期望岗位”明确写出来？
- 技术项目要偏业务价值还是偏技术深度？
- 应届生/初级候选人是否需要降低动词强度？
- 是否需要把项目从“技能展示”改成“业务/工程交付证据”？
- 是否需要给出当前可投递版本 + 7 天补强任务？

## 阶段 5：快速完整稿

默认先产出完整稿，不要让用户先回答十几个问题。

快速稿要求：

- 结构完整。
- 语言像真实候选人，不像广告文案。
- 工作、实习、项目和校园经历中的每条职责 bullet 使用 `- **小标题**：正文`；只有整段压缩成一行概述时可以不使用 bullet。
- 小标题一般为 4-8 个汉字或相近视觉长度，使用业务对象、功能模块、问题类型或结果命名；中英混合技术标题可适当放宽，不为凑字数牺牲准确性。
- 每条 bullet 尽量有：场景、问题、动作、工具/方法、结果。
- 没有结果就写交付物或完成情况，不编数据。
- 技术项目保留能区分方案的实现细节，用小标题分区、完整句子表达；不要用大量 `/`、`+`、`→` 压缩成难扫读的文本块。

## 阶段 6：选择式 STAR 补强

读取 `guided-star-interview.md`，并读取 `star-option-example-library.md` 中与目标岗位对应的章节。

只挑最影响投递的 1-2 段经历。每段最多五步：

1. 场景与规模。
2. 任务与目标。
3. 关键难点。
4. 解决动作。
5. 结果与数据。

前台一次只显示一个问题。每题必须有：真实进度、3-6 个选项、跳过入口、自由补充入口、同岗位短案例。

优先补的证据顺序：

1. 具体动作与工具。
2. 工作量、范围、周期和频率。
3. 难点、约束与取舍。
4. 前后变化或结果数字。
5. 没有数字时的交付物、验收或采用证据。

角色边界、已有数字口径、材料冲突或技能真实性需要单独确认时，再读取 `question-bank.md`。不要问“还有什么想补充的吗”。

## 阶段 7：局部重写

用户回答后，不要整份简历推倒重来。先判断回答影响哪些模块：

- 只影响一段项目：只重写项目。
- 影响个人优势：重写个人优势和对应经历。
- 补了新技术：检查经历中是否有证据，再更新技能。
- 补了目标方向：重写策略、个人优势、经历排序。

重写后做一次短统稿，保证全篇风格一致。

一段五步完成或提前达到结束条件后，必须回读：

- 用户答案形成的事实摘要；
- 1-2 条简历 bullet；
- 一段 30-60 秒的自然 STAR 讲法。

明确等待用户确认或修正，再把新增内容标为已确认。参考案例不得进入回读内容。

## 阶段 7.5：岗位能力证据卡与追问预演

读取 `capability-evidence-cards.md`。

- 为每条强 bullet（有数字、有强动词、有独特卖点的）从事实台账生成岗位能力证据卡，一般 5-8 张。
- 每张卡先标明通用能力维度，再按 JD 标明岗位专业能力；标题使用“通用能力｜岗位专业能力｜对应经历”，不显示内部编号。
- 对每张卡做追问预演：模拟面试官 3 个追问，台账里答不上来的 bullet 降级或重写。
- 预演失败的改动要回到阶段 7 局部重写，不能只删卡不改简历。

## 阶段 7.8：项目复盘手册与作品集

当用户提供项目截图、PPT/PDF、视频、压缩包或要求“所有简历 + 对应作品集/飞书文档”时，读取 `feishu-project-handbook.md`。

- 先按事实台账和岗位方向确定同一项目在不同简历中的展示角度，项目时间、角色、技术栈、结果和奖项保持一致。
- 用户要求完整交付时，默认同时生成两份：项目复盘与面试准备手册、面试官外发作品集；只有用户明确缩小范围时才减少。
- 先从事实台账生成两份文档共用的事实型正文核心，采用候选人/项目视角和面试官可读标题；准备手册不得以“这份文档怎么使用”“面试时怎么讲”等教学式标题打断展示链路。
- 准备手册按“演示视频 → 项目速览 → 系统全景 → 个人职责 → 核心链路 → 功能证据单元 → 测试/协作/交付 → 深入理解与核验 → 追问准备”组织。
- 外发作品集从事实台账和事实型正文核心独立生成，按“演示视频 → 一句话项目概述 → 系统全景 → 个人职责 → 核心证据 → 结果与交付物”组织，不从内部手册机械删减。
- 精选能形成证据链的图片并逐张解析，补 3—5 张真正帮助理解关系和流程的图，不倾倒全部素材。
- 准备手册可以补充常见实现和排障知识帮助用户理解；需要用户学会后复制的内容，先给核验清单，再给完整候选人段落。未经核验不得迁入外发作品集。
- 用户要求飞书时，分别完成两份文档的实际媒体绑定、权限设置、所有权转移与元数据核验，并把两个最终链接写回本地交付目录。

## 阶段 8：最终审查

读取 `final-audit.md`。

交付前必须查：

- 有没有编造。
- 有没有过度动词。
- 经历区是否每条职责 bullet 都带加粗小标题；发现漏项必须返回阶段 7 修正。
- 有没有技能没证据。
- 有没有数字没口径。
- 有没有把选项区间改成精确数字。
- 有没有把参考案例混进用户事实。
- 有没有 AI 味词。
- 技术岗有没有乱加术语。
- HR 看不看得懂。
- 面试官能不能追问下去。
- 双读者 checklist 是否双跑通过（读取 `dual-reader-rewrite.md`）。
- 强 bullet 能力证据覆盖率：每条强 bullet 是否都有岗位能力证据卡。
- 生成项目手册/作品集时，是否通过 `feishu-project-handbook.md` 的内容、视觉、媒体、权限和所有权验收。

## 推荐输出节奏

默认使用 Markdown，并按受众拆分。不要把顾问备注、风险和训练内容混进可外发简历或作品集；不要自动转换为 DOCX/PDF，用户明确要求时再处理。

### 第一次处理材料

```text
内部优化交付：打法、确认项、diff、岗位能力证据卡、事实台账、风险
外发完整版简历：只有候选人希望招聘方看到的可验证内容
外发项目作品集（有项目材料且完整交付时）：只含可核验项目事实、个人贡献、关键截图、解析和交付物
项目复盘与面试准备手册（有项目材料且完整交付时）：沿用外发式事实正文，并增加实现理解、核验、问题解决、追问和练习
```

如果候选人缺少可验证证据，只在内部文件加：

```text
六、建议补强的作品/交付物
```

### 用户补充后

```text
内部优化交付：已更新事实、受影响模块、新 diff、剩余缺口
外发完整版简历：同步更新受影响模块，不带修改说明
外发作品集：事实或作品内容变化时更新；不得自动吸收内部补充
项目准备手册：同步更新事实型正文、岗位能力证据、实现解释、核验项和追问
```

### 最终交付

```text
姓名-目标岗位-简历优化交付.md
姓名-目标岗位-完整版简历.md
姓名-项目名-项目作品集-飞书版.md（有项目媒体且完整交付时）
姓名-目标岗位-工作样本与面试培训.md（需要作品/培训时）
姓名-项目复盘与面试准备手册-飞书版.md（有项目媒体或要求飞书时）
```

交付前对外发文件做受众隔离审查：搜索并清除内部提示、占位符、事实编号、风险词和培训话术；无法确认的内容从外发文件删除，不以隐藏或伪装方式保留。
