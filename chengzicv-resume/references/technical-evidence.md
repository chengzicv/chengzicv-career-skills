# 技术经历：范围、机制、演进与证据

适用后端、AI 工程、系统实现类经历。用于技术内容的选择和保留，不另设项目格式。真人稿只用材料支持的事实，虚拟案例可以设计独立情境但不能复制真实身份、贡献或业绩。

## 先看整个项目，再写局部

背景说明使用对象、项目用途和边界。职责先让读者知道本人承担哪些模块、模块如何连接，再选有材料的部分讲机制。不要只留下功能清单，也不要把完整项目写成几次零散故障处理。

条目可以分别承担功能范围、核心实现、方案演进、验证交付，不要求每条都有问题—解决—提升。没有漂亮数字时，已完成流程、测试、部署、版本记录、源码或文档也能说明完成情况。证据类型不同，不互相代替：代码不证明生产规模，仓库星数不等于个人贡献，演示不等于上线。

## 从具体机制组织技术重点

先在内部为每个项目写一句“读者最该记住的技术工作”，再写职责。可以是核心能力、架构取舍或边界条件，不强制制造故障故事。完整简历的项目应有不同侧重；不要让每段都重复幂等、重试、灰度和回退。通用机制只有承担不同判断时才详细展开。

区分三层：组件名（线程池）→措施（有界队列与超时）→机制（出队核对剩余预算，已发出的超时请求查单确认）。重点条目应写到材料支持的机制层：什么条件下，哪个对象/状态如何处理，为什么这样处理。不是每条都填满这三个问题，也不按参数数量评分。

真人改写只发现、前置和无损组织已有技术事实。原文只写“配置线程池”，不能从本范例复制截止时间、拒绝策略或远端查单；记录缺口即可。冲高必须有独立证据锚点，范例不是锚点。全虚拟案例可以先设计自洽的机制，再写结果，不能先填提升百分比再反推实现。

技术抽查：暂停重试或打乱执行顺序，原有方案是否仍说得通？配置阈值、故障保护、测量结果是否混用？比较数据是否验证本条机制，而非只证明换了整套系统？简历不是设计文档，只需保留决定性关系，计算与测试推演留内部。

完整技术案例可按需读 [直述体项目示范](exemplar-benchmark.md) 的技术项目示例，理解项目重点与机制颗粒度，不复制题材、数字、人物或「两任职三项目」配额。局部真人改写默认不加载整份范例。

## 保护实现关系，不只保护术语

逐项找回材料中的：

- 输入与输出、模块之间的调用和状态变化；
- 触发条件、执行顺序、隔离粒度、资源继承或共享边界；
- 并发上限、超时、批量阈值及单位，阈值是“或”还是“且”；
- 失败后的重试、降级、回退、检查点和恢复范围；
- 数据写入、缓存失效、消息去重和事务边界；
- 旧方案、新方案、调整原因，以及改后仍存在的代价和限制。

不要求补齐所有项，只保护材料已经有的关系。保留 Redis、异步、检查点等词，却删了何时触发、谁隔离、恢复什么，仍算丢信息。必要时拆句，不压成“优化架构、完善机制”。

## 技术名词先判断阅读价值

简历不罗列内部变量名、字段名、状态常量或无辨识价值的类名。将名称转换为准确含义，保留它对应的对象、触发条件、状态关系、数值和结果。原始标识留在内部事实记录，不能把换掉名字当成删除机制。用户明确要求代码级说明时按其范围处理，不把该例外变成简历默认写法。

- 保留用于岗位匹配的技术栈与常见专业概念，如 Java、Redis、Elasticsearch、线程池、事务、幂等、游标分页。
- 实现专用的API、策略类名与缩写，默认先写中文用途。只有该名称本身能证明岗位要求的具体经验，或用户明确希望保留，才在已说明用途后保留必要名称；不把原来的术语堆搬到括号里。
- 标题先说明这一条做了什么，例如“下单超时与线程隔离”“订单列表稳定翻页”“任务恢复与结果复用”。不要用一组API或常量作为标题。专业标题仍可用，但读者不应先查该组件文档才理解内容。
- 面向同岗位工程师，不要求零技术读者看懂全部，也不假设同行熟悉每个组件内部命名。测试是：即使不知道该API名字，仍能读出动作、条件与取舍。

等价改写示例（不是可移植事实）：
- TRY / CONFIRMED / CANCELLED → 预占、确认、取消；仍说明取消先到如何拦住迟到预占。
- CallerRuns → 队列满时不让下单线程执行库存调用；不能因删类名改变拒绝行为。
- run_id / step_id → 任务编号 / 步骤编号；计划改版与恢复边界继续保留。
- CDC → 订阅数据库变更，增量更新索引；PIT＋search_after → 固定查询快照，按上一页位置连续读取。保留数据版本与翻页限制，不能泛化为“提升查询性能”。

这项规则约束下文截图与所有范例的呈现；原始截图术语只是来源转述，不是要求照抄的推荐成稿。

## 技术标题与动词

标题可以是 Agent 并发调度、Middleware Chain、JWT 会话撤销、上下文压缩与检查点恢复。是否合适看正文和岗位，不能只凭英文、术语或字数判断。仅有“JWT+Redis”时补说明处理什么，不一律改成“登录优化”。

设计、实现、构建、集成、架构不是禁词。正文要说明对象、本人动作和机制。删无信息评价，不把准确技术表达全部换成“用、把、做了”。

## 材料有演进时，保留前后关系

例如固定节点流程变为动态调度，重点保留原流程限制、调度方式与控制条件，不只写“升级多 Agent 架构”。有中间轮次和未采用方案时，保留它们解释的判断。没有历史版本或失败经历，不为显示资深而补造。

资深岗位可体现模块边界、扩展方式、上线迁移和运维判断，但实际层级依材料/JD。校招、实习也可有深实现，不能因为职级低删技术细节，也不能因为做得深自动写成项目 Owner。

## 对照样本：学习颗粒度，不搬经历

以下摘点来自用户提供的三张后端/AI 简历截图，均为局部转述。第一张右侧有截断，仅使用可辨识部分。用户说案例已进入大厂，这不是这些写法导致录用的证明。示例不是可挪用的个人事实。

### 截图一：Agent 调度

可辨识信息：Sub-agent 最多 3 并发、单任务超时 900s、继承父线程目录、复用父沙箱。

丢信息写法：构建高效多智能体调度体系。

保留细节的片段：
- **Agent 并发调度**：限制 Sub-agent 最多 3 个并发，单任务超时设为 900 秒。子 Agent 继承父线程目录并复用父沙箱。

不能凭此补成每个子 Agent 拥有独立沙箱，也不能把配置上限写成实测吞吐。

### 截图一：Skill 加载

可辨识信息：每个 Skill 独立目录，包含 SKILL.md，system prompt 注入索引，按需读取全文。

保留细节的片段：
- **Skill 按需加载**：每个 Skill 使用独立目录和 SKILL.md，system prompt 只注入索引，需要使用时再读取全文。

不能额外断言节省多少 Token，不把新增目录可扩展改成自动热更新。

### 截图二：会话与异步客户端

可辨识信息：每次对话创建独立异步 AI/TTS 客户端，原文将共享客户端与用户间阻塞联系起来。

保留细节的片段：
- **会话客户端隔离**：为每次对话创建独立的异步 AI/TTS 客户端，替换原先共享客户端的方式。

隔离对象是客户端实例，不应改写成独立进程。具体阻塞根因与改善程度需回到实现或测试，不因截图写了“彻底消除”就升级为已验证效果。

### 截图二：日志批量写入

可辨识信息：文件、数据库、Redis 分层，5 秒／50 条触发 flush，Redis 缓存热点日志。

必须保留存储分工、刷新阈值和单位。但截图没有把两个阈值的逻辑关系讲透，不擅自补成“同时满足”；改写时保留原口径并在正文外核对触发条件。“减少 90% 数据库往返”另查测量口径，不由阈值直接推导。

### 截图三：两种交易方式与状态流转

可辨识信息：出售和求购悬赏，悬赏包含投稿、买家选择、收货确认、按比例分账。另一项目明确包含仿真物流与模拟支付。

保留工作范围，再展开状态条件与实现。不要把整条流程删成“实现电商闭环”，不要把“模拟/仿真”删成正式接入，也不能将截图不同项目合并为一个人的同一套实现。

## 引用案例时的真实性检查

截图是候选人的陈述，不是技术正确性、性能或任职背书的外部核验。身份、学校、公司、链接、Owner/Committer 称号和个人数据不进入通用示例。

看到黑名单删除/增加的语义不清、UUID 与锁竞争之间缺论证、笼统高并发/高可用或提升百分比时，列具体待核验点，不自动纠正成另一套没证据的实现，也不把不确定说法写成教程。输入截图缺页或裁切时明确缺口，不猜补文句。

## 最后检查

遮住框架名后还能否看见具体动作？保留框架名后能否解释动作与约束？范围、机制、演进和证据是否按原材料保留，而不是都变成故障—优化—提升？标题有辨识度且没有夸大角色？能回答这些问题才算保留了技术含量。
