# 公司内垂直虚拟案例深度标准

当用户要求“更垂直、更深、模拟一家公司、把项目放进公司、像真实业务项目一样完整”时，除 `fictional-resume-case.md` 外必须读取本文件。

本标准定义的是案例的业务深度，不是固定行业模板。不要复用袋泡茶、招聘、SaaS 或任何上一次案例的公司、数字和项目。

## 一、什么叫达到深度？

深度不等于流程更长、数字更多或术语更专业。一个公司内案例至少要形成下面这条因果链：

```text
公开行业依据
→ 虚拟公司原有业务
→ 现有经营问题
→ 为什么立项
→ 候选人在组织中的职责
→ 项目执行与跨角色协作
→ 成本、渠道、质量或交付约束
→ 可核对的经营结果
→ 继续、修改、暂停或停止的决策
```

如果删掉公司名称后，项目仍然像一份通用课程作业，说明深度不足。

## 二、四层事实必须分开

| 层级 | 内容 | 规则 |
| --- | --- | --- |
| 公开事实 | 行业、法规、产品、价格、渠道和岗位资料 | 附来源；时效性内容需要检索核验 |
| 虚拟公司事实 | 公司规模、业务模式、组织、渠道、SKU和经营基线 | 明确标注模拟，不冒充真实企业 |
| 虚拟项目事实 | 研究、成本、过程、结果、库存、失败和决策 | 先建计算台账，再写简历和作品集 |
| 用户真实事实 | 用户实际经历和证据 | 不得自动吸收前三层内容 |

公开品牌只能用于行业对标，不能把其销量、工厂、渠道或组织直接复制给虚拟公司。虚拟公司名称不得与真实企业混淆。

## 三、调研最低要求

用户明确要求调研，或案例依赖当前市场、法规、平台和岗位信息时，必须先检索再构造案例。

至少覆盖三类资料：

1. **真实产品与商业形态**：品牌官网、官方店铺、公司公告或公开产品页，用来确认行业里真实存在什么SKU、价格、渠道和服务方式；
2. **规则与专业约束**：政府、标准、平台官方规则或行业主管机构，用来确认合规、质量、交付和平台边界；
3. **岗位要求**：企业招聘官网或当前公开JD，用来确认岗位实际负责的动作、指标、工具和协作对象。

第三方市场规模、增长率和排行榜只能作为方向信号，必须说明它是估算或报告口径，不能据此倒推虚拟公司的销量。

调研结论要进入项目选择与约束，不能只放在作品集开头充当背景介绍。

## 四、虚拟公司最小模型

模拟公司至少写清：

- 公司名称、品牌或业务线；
- 所处城市、发展阶段和大致人数；
- 卖什么、卖给谁、通过什么渠道成交；
- 自研、自制、OEM、采购或服务交付方式；
- 原有核心产品、客户或项目；
- 一项与本项目直接相关的经营基线；
- 项目涉及的团队和汇报关系。

推荐用一张公司卡和一张小型组织图表达，不编造冗长融资史、创始人故事和与项目无关的部门。

公司基线必须能回答：

```text
这家公司为什么现在要做这个项目？
如果不做，会继续损失什么或错过什么？
它已经拥有哪些资源，又缺什么？
```

## 五、项目必须由经营问题触发

项目起点优先使用公司已有问题，而不是“行业很热，所以决定做”：

- 原SKU转化、退款、复购或库存异常；
- 某类客户流失、交付超期或报价失败；
- 渠道费用上涨、价格带缺口或利润结构变化；
- 某个功能使用率低、客诉集中或销售周期过长；
- 原流程存在重复劳动、漏项或质量风险。

项目目标应同时包括：

1. 业务结果门槛；
2. 时间或预算上限；
3. 暂停、停止或不扩大投入的条件。

没有停止条件的模拟项目，容易变成只追求成功数字的宣传稿。

## 六、岗位与组织边界

必须列出候选人的直属上级、协作角色和最终决策者。对每个关键模块说明：

- 候选人实际执行什么；
- 候选人整理或提出什么；
- 哪些事项由主管、专业人员或其他团队确认；
- 哪些团队成果不能全部归到个人名下。

公司内案例可使用以下结构：

| 模块 | 候选人 | 直属主管 | 专业团队 | 业务团队 |
| --- | --- | --- | --- | --- |
| 需求 | 整理、分析、起草 | 确认优先级 | 提供专业判断 | 提供业务数据 |
| 方案 | 维护版本、跟进 | 最终确认 | 审核可行性 | 评估渠道或客户适配 |
| 上线/上市 | 记录、核对、复盘 | 决定发布 | 完成交付与验收 | 执行销售或运营 |

初级候选人优先使用“整理、起草、维护、跟进、测算、复盘、提出建议”。除非角色设定和组织权限支持，不写“制定公司战略、操盘整个渠道、独立研发、决定全部预算”。

## 七、项目阶段门

根据岗位选择实际阶段，不机械套全部环节。完整公司项目通常至少包含：

```text
经营基线
→ 研究与问题定义
→ 方案或产品定义
→ 专业可行性与供应商/研发/交付验证
→ 成本、收益或资源测算
→ 小范围上线/上市/试运行
→ 结果、异常和后续决策
```

每一阶段需要有：

- 输入材料；
- 候选人的动作；
- 可检查的交付物；
- 进入下一阶段的条件。

流程图只解释关系和决策，不把所有文字重复画一遍。

## 八、经营数字与计算台账

详细数字先放内部台账，简历只保留最有辨识度的少量数字。

存在交易、投放、交付或漏斗时，至少核对：

```text
起点数量 ≥ 中间数量 ≥ 结果数量
```

并根据行业区分以下口径：

- 访问、线索、意向、支付、净订单、交付、复购；
- GMV、含税收入、净收入、商品毛利、贡献毛利和净利润；
- 采购成本、履约成本、平台费用、佣金、投放、退款和损耗；
- 首批数量、已售数量、售罄率、剩余库存和库存现金；
- 预计模型与上市/上线后的实际模型。

有公式的数字必须能重算。示例：

```text
支付转化率 = 支付订单 ÷ 有效访问
退款率 = 退款或取消订单 ÷ 支付订单
净售罄率 = 净订单 ÷ 首批可售数量
单笔贡献 = 净收入 - 随订单变化的商品、履约、渠道和售后成本
```

不要把贡献金额写成净利润，不要把意向写成订单，不要把团队GMV全部写成个人业绩。

## 九、必须出现真实取舍

深度案例至少包含两个可解释的取舍，其中至少一个是“不继续做”：

- 没有选择报价最低但起订量或交付风险更高的供应商；
- 某个版本流量高但转化差，因此没有继续投放；
- 单笔毛利为正但库存周转未达门槛，因此没有补货；
- 功能上线数据不差，但客诉或运维成本过高，因此暂停扩量；
- 项目达到局部目标，但没有夸大为整体成功。

取舍必须写清比较对象、判断指标和放弃的代价。只写“综合考虑后选择方案B”不算。

## 十、深度案例成套交付

用户明确要求“垂直深度案例＋简历＋作品集”时，默认交付四份相互独立的 Markdown：

1. **内部调研与设计说明**：公开来源、虚拟公司模型、事实分层、计算台账、岗位能力模型和风险；
2. **教学案例示例简历**：按 `fictional-case-realism.md` 建立候选人身份、个人优势和校园证据链，再把公司项目放进对应工作经历；
3. **教学案例工作样本**：公司背景、职责、项目主线、证据、结果和决策，顶部保留非真实案例披露；
4. **教学案例面试准备手册**：数字口径、角色边界、60秒/3分钟讲法、追问和不能说错的地方。

若用户明确只要其中一项，按用户范围缩减。文件名或标题使用“案例/示例”表明材料属性，每份材料至少保留一个清楚且不可遗漏的教学披露点；正文模块不反复添加“虚拟/模拟”。

作品集不等于把设计说明删除几段。两者受众不同：设计说明解释为什么这样构造；作品集让招聘方判断候选人如何工作。

## 十一、简历写法

用户要求把项目放进模拟公司时：

- 公司项目不能替代应届候选人的身份与校园证据；是否单列校园模块按 `fictional-case-realism.md` 判断；
- 公司作为一段工作或实习经历出现；
- 日常职责先说明长期接住什么工作；
- 重点项目作为该公司经历中的子项目，而不是伪装成独立创业；
- 项目 bullet 优先展示问题、个人动作、经营结果和一个反常识取舍；
- 详细研究、公式、流程和交付物进入作品集，不把简历写成项目报告。

每条经历职责仍使用 `- **小标题**：正文`。同一条 bullet 最多保留1—3个有关系的数字，避免把完整台账塞进简历。

## 十二、最终深度检查

- [ ] 公开事实、虚拟公司、虚拟项目和用户事实已经分层；
- [ ] 行业、规则和岗位要求有可追溯来源；
- [ ] 公司有原业务、组织、资源和经营基线；
- [ ] 项目由公司问题触发，不是因为“行业很热”；
- [ ] 候选人、主管和协作团队的职责边界清楚；
- [ ] 项目有预算/时间上限和停止条件；
- [ ] 漏斗、收入、贡献、售罄和库存等公式可重算；
- [ ] 至少有两个业务取舍，其中一个是没有继续投入；
- [ ] 结果同时说明达成、未达成和下一步决策；
- [ ] 交付物能证明候选人具体做过哪些动作；
- [ ] 简历保持克制，深度主要由作品集和准备手册承载；
- [ ] 案例不能被误认为用户真实经历。
