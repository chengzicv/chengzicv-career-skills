# 经历句子的直述写法

写法以 `plainspoken-resume-style.md` 为准。每条让读者看懂候选人做了什么、怎样做，以及有依据的结果。

## 从动作展开

用具体动作或必要场景开头，直接接对象和做法：核对哪类数据、排查哪个接口、怎样测试、向谁交付。句首动词保持普通字体。不为每条加无信息量的空标签（如"核心链路优化"这类换个项目也能用的词）；材料中有具体机制、对象或能力域名称时，可以使用具体标签（如"GIS 点位渲染优化：""用户研究与需求分析："），让读者一眼看懂这条讲什么。

“负责、参与、协助、维护”可以说明真实角色。问题在于其后缺少具体工作，不能为了显得更强改成没有依据的“主导、自研、重构”。专业名词跟随候选人实际材料，不为增加技术感植入组件或方案。

## 对象、方法与结果

这三个角度用于检查信息，不要求每条同时凑齐：

- 对象：具体接口、组件、文件、业务场景、渠道、客户类型或协作部门。
- 方法：怎样操作、为何选择该方案、怎样处理失败或异常、怎样核对实际影响。
- 结果：真实数字、交付物、验证记录、使用范围或完成状态。

项目结果可以集中在最后一句。没有测量结果就不补延迟、准确率、增长率和“100%”。保留结果的时间、单位、基线与自测／线上口径。

## 背景、动作、成果

核心项目通常先用一两句说明已知背景，再列 3~4 个动作，最后写实际成果。条数按材料决定，不强制标签。没有结果材料时写到已知动作为止；简短局部修改不自动补整段背景。

## 加粗与长度

只加粗少量核心实体和结果，不加粗整句或整段，不用固定比例决定内容。单条约 35~45 个汉字是紧凑参考；长句可以按真实工作拆分，短句无需填词。技术符号、英文名称和异常处理条件完整准确优先。

## 措辞示范

以下是虚构的措辞练习，不能当作当前候选人的事实：

```markdown
- 使用 Burp Suite 对比不同账号访问同一订单接口的返回结果，核对登录身份和订单归属。
- 对比投放渠道的点击和咨询记录，整理用户最常询问的问题，调整下一轮内容选题。
- 核对报销单中的发票信息与付款记录，将金额不一致的记录退回经办人补充说明。
```

这些句子用具体操作支撑专业能力，没有无依据的效率数字。材料确有高价值数据时，保留数据和口径，而不是为追求口语化删掉。

终检时读一遍：去掉加粗后句子是否顺畅，读者能否看懂动作对象，是否有只为包装而添加的词，是否删掉了重要的方法和边界。
