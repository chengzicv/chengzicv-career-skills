# 简历的口语化直述体

核心写法借鉴 jc-knowledge-capture 的直述体表达规则，在这里统一用于简历、经历描述与面试回答。本文是 ChengziCV 内部的完整写作规则，无需调用其他 Skill。

目标是让简历像一个人把事情想清楚以后，直接、自然、准确地说出来。后续生成和改写默认采用这种写法；用户明确指定其他风格、保留原话或只修格式时，按本次要求执行。

## 先说要说明的事，再补解释

先写这一句真正要说明的动作、能力或成果，再补对象、做法、原因和条件。不要先铺很长的背景，也不要用提问拖延答案。

材料中确有难点或问题时，可以在同一句内先交代问题再接方案（"针对……的问题，做了……"）。这是难点前置，一句内完成，不算铺背景；经核实的大厂入职简历普遍采用这种结构。独立成段、超过两句且不含候选人动作的纯背景仍然不写。

每条围绕一个主要意思展开。紧密相关的操作可以写在一起，互不相关的任务分开写。材料很短时只写已知内容，不为了完整硬补例子和边界。

## 直接写具体对象、动作和方法

优先写候选人对什么对象做了什么，怎样处理，怎样验证，以及得到什么有依据的结果。

- 对象要具体：系统、接口、数据、工具、文件、渠道、客户或协作部门。
- 动作要实际：核对、排查、抓包、验证、开发、整理、测试、沟通等，跟随候选人的真实分工。
- 方法要有内容：说明怎样操作、怎样处理异常、为什么选择该方案，避免只写“优化、提升、完善”。
- 结果要有依据：真实数字、交付物、测试记录、覆盖范围或完成状态均可，不要求每条都有数字。

抽象判断必须落到真实对象、场景或动作。优先使用材料中已有的信息，不凭空编故事、数字和经历。不生造模型名称、概念链或宏大口号，也不删掉有价值的专业词、处理机制和验证条件。

## 自然表达，清理噪音

使用适合求职场景的书面白话。句子可以有长有短，但每条只推进一个主要意思。不要为了口语化强加口头禅，也不要把每句话加工成金句。

删除重复、无意义停顿和转录噪音，例如“那个那个”“然后然后”。整理聊天记录时，合并重复信息，去掉提问者、顾问、检索过程和生成过程留下的对话壳。

正文不写“根据资料”“AI 认为”“接下来逐一回答”“思考过程”等制作旁白。AI、Skill 或代码仓库确实属于候选人的工作工具和成果时，保留该事实。引用和来源确有必要时保留归属。

旁白禁令同样覆盖以下两类，判据只有一句：这句话是写给面试官看的，还是写给候选人本人看的？后者一律移出正文：

- **防御性口径声明**：解释自己为什么不写某内容的句子，如“用户量不大、也没做过压测，所以不写并发指标”“这块没有数据，只写过程”。这类句子暴露短板且对面试官无信息，正文删除；确有必要说明时移入小抄、确认台账或交付说明。
- **占位符**：`〔姓名〕`、`【待补】`、`XXX` 等一律禁入正文。信息未确认时正文用中性表述兜底（如标题位写岗位名），缺项列入交付说明或追问清单。

## 语气明确，保留事实边界

已确认事实可以直接写。材料只是推测、个人理解或方案建议时，保留相应限定，不把相关性写成因果，把偏好写成事实。

区分个人与团队、参与与主导、学习与实操、自测与生产、分析与开发。完成到哪个阶段就写哪个阶段；不为了句子有力把本地 Demo 写成上线，把辅助工作写成独立负责。

有数字时保留时间、单位、对象和口径。没有测量结果时写实际交付和验证，不填入效率、准确率或性能数字。冲高候选补全沿用主技能的材料规则，全部在小抄中说明依据与事实回退句。

## 少用反转和空泛强调

直接呈现事情，少预设读者犯错。不额外设置材料里没有的错误观点，再通过纠正它显示专业。

默认不用以下句式及其近似变体制造反转、对抗或空泛强调：

- 不是……而是……
- 不在于……在于……
- 不需要……需要……
- 不会……会……
- 真正的……是……
- 与其说……不如说……

不能只换同义词规避限制。“本质是”“底层逻辑是”也不能代替解释。优先直接说明对象、动作、原因与条件。

准确性所需的事实对比、排除和技术边界可以保留，例如“这是本机自测，不是线上容量”。忠实保留原话、直接引语或分析句式时也可保留。改写不能改变原有事实、否定关系和限定，不用固定次数配额。

## 结构跟随材料

使用常规简历模块。每段经历（工作 / 实习 / 项目）的结构固定为：标题行（时间、名称、真实角色）→ 一行加粗的「**背景：**」→ 动作 bullets（单层 `- `）→ 有依据的成果自然句收尾。

「背景：」标签固定加粗写成 `**背景：**`。只写一句，交代候选人面对的场景、旧方案的痛点或要解决的问题（借鉴 GodSU resume-crafting 的经历骨架"背景与目标"）。这一句必须有信息量：写得出痛点就写痛点，写不出就写业务场景和规模，不允许空泛。

除「背景：」外，默认不打印"项目简介：""负责内容：""取得成果："等套话标签，也不为每条动作加空泛的伪小标题（"核心链路优化"这类换个项目也能用的词）。材料中有具体机制、对象或能力域名称时，可以使用具体标签（如"GIS 点位渲染优化：""用户研究与需求分析："），让读者一眼看懂这条讲什么。

核心项目通常写 3～4 条动作，材料少时可以更短。未提供结果的经历写到已知内容为止。用户明确要求保留标签或原模板时，保留格式并使用直述句。

加粗集中在少量核心实体和结果，不加粗整段。字数和行数辅助阅读，不能让句子失真，也不能成为增加空行、重复内容或虚构经历的理由。

以下为虚构的措辞练习，只用于理解写法，不能当作当前候选人的经历：

```markdown
**[时间]　授权 Web / API 安全测试　渗透测试人员**

对客户授权的业务接口开展测试，检查登录身份、用户权限与数据归属，提交报告并跟进修复。

- 使用 Burp Suite 对比不同账号访问同一资源的返回结果，核对接口权限。
- 将漏洞触发条件、复现步骤、截图和实际影响写入报告。
- 向开发人员解释修复建议，修复后按原条件再次验证，记录复测结果。

交付资产清单、漏洞报告和修复复测记录。
```

## 两版共享写法，分别选择重点

冲高版重点解释材料中的难点、机制、方案取舍、验证和代表成果；稳健版重点说明工作范围、个人动作、协作与交付。两版都自然直述，都保留有分量的成果，不靠夸大形容词或删除专业内容区分。

「个人优势」块用另一套结构：按背景 / 能力 / 产出 / 荣誉四层写完整句（层叠事实式，规则见 `advantage-block.md`），每层一个 `- **标签：**内容`，不写片段式信号行，也不用 `·` 分隔。其余头部成果同样用完整句交代平台或项目、候选人的动作和结果。榜单时间、积分、官方评级、单次与累计奖励保持原始口径。只有材料确认某笔奖励属于指定案例时，才能关联；最高单洞奖励不能自动归到旁边列出的漏洞。

## 交付前读一遍

- 每句是否在说明具体事情，是否有只为包装而加的词？
- 对象、动作、方法和有依据的结果是否清楚，专业细节是否保留？
- 是否保留真实分工、完成阶段、否定关系和不确定性？
- 是否避免空泛反转、概念包装和制作旁白？
- 去掉标题和加粗以后，句子是否仍然自然成立？

完整优化直接交付采用这种风格的两版与小抄。只改一段或一条时，完成指定范围，不自动生成重复版本。
