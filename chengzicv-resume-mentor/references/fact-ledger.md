# 事实台账

事实台账是这个 Skill 的核心。不要依赖模型记忆，先把材料拆成事实。

## 为什么要做事实台账

改简历最容易出问题的地方不是句子不漂亮，而是：

- 把建议写成事实。
- 把参与写成主导。
- 把没用过的技术写进技能。
- 把没口径的数据写成成果。
- 多份材料互相冲突，模型自己选了一个。

事实台账解决这些问题。

## 事实分级

| 等级 | 含义 | 能否写入最终简历 |
| --- | --- | --- |
| 已确认 | 原文明确或用户确认 | 可以写 |
| 待验证 | 原文暗示但不完整 | 可保守写，避免强结论 |
| 推断 | 基于行业常识推断 | 不写入事实，只能作为追问 |
| 有冲突 | 多材料冲突 | 不写，先问 |
| 禁止使用 | 高风险或无来源 | 不写 |
| 未来计划 | 尚未发生、仅计划后续执行 | 不写成已完成经历或成果 |

## 访谈来源与颗粒度

选择式 STAR 访谈产生的事实必须额外记录来源方式和颗粒度：

| 字段 | 可用值 | 说明 |
| --- | --- | --- |
| 获取方式 | 用户原文 / 用户选择 / 用户补充 | 区分材料与访谈回答 |
| 颗粒度 | 精确值 / 约数 / 区间 / 量级 / 定性 / 交付物 | 决定最终可以写到多具体 |
| 对应步骤 | 场景规模 / 任务目标 / 关键难点 / 解决动作 / 结果数据 | 对应五步状态机 |

参考案例、选项中未被用户选择的内容、为帮助理解而给出的数字，一律不是事实，不进入台账。

## 中文编号规则

- 面向用户的事实按出现顺序写成“事实1、事实2、事实3”，不要使用英文前缀、下划线或补零编号。
- 材料来源写成“来源1、来源2、来源3”，保持与事实引用一致。
- 状态只使用上表中的中文名称，不输出英文枚举值。
- 删除事实后可以重新连续编号；最终交付不保留无意义的缺号。

## 台账结构

```json
{
  "事实": [
    {
      "编号": "事实1",
      "来源": "来源1",
      "模块": "项目经历",
      "原文": "原文片段",
      "标准化事实": "标准化事实",
      "事实状态": "已确认",
      "获取方式": "用户选择",
      "颗粒度": "区间",
      "对应步骤": "场景规模",
      "简历用途": "可用于项目经历",
      "能力证据卡": "问题分析与业务判断｜前端问题排查｜互动绘本异常处理",
      "风险": "无",
      "待确认问题": []
    }
  ],
  "待验证主张": [
    {
      "主张": "效率提升50%",
      "来源": "来源1",
      "问题": "缺少原始耗时和优化后耗时",
      "确认问题": "这个50%是怎么计算的？比如原来10分钟，现在5分钟吗？"
    }
  ],
  "冲突": [
    {
      "字段": "项目时间",
      "来源甲": "2023.03-2023.06",
      "来源乙": "2023.05-2023.09",
      "确认问题": "这个项目最终应该写哪个时间段？"
    }
  ]
}
```

## 抽取规则

### 可以直接抽取

- 公司、学校、专业、时间、职位、项目名。
- 原文出现的工具、技术、方法。
- 原文出现的数据、人数、金额、比例、周期。
- 原文明确写出的交付物。
- 用户明确说“我做了”的动作。
- 用户明确选择的选项所表达的内容；只能按选项原有颗粒度记录。

### 选择式答案转换

- 选择“2-5 个模块” → 记录区间 `2-5 个模块`，不得改成 `3 个模块`。
- 选择“数百条数据” → 记录量级 `数百条`，不得改成精确行数。
- 选择“明显减少但没统计” → 记录定性变化，不生成百分比。
- 选择“完成 FAQ/SOP/报表” → 记录交付物，不推断已被采用。
- 选择“记不清/跳过” → 不生成新事实。

### 需要降级处理

原文写“负责”，但用户是应届/实习/项目成员，且没有上下文证明主导时：

- “负责”可改为“参与”“协助”“支持”“跟进”“完成”。

原文写“主导”，但没有团队规模、决策权、最终责任时：

- 改为“参与推进”“承担其中的XX模块”“在导师/主管指导下完成”。

原文写“提升50%”，但没有口径：

- 若能从原文补出口径，写“从 A 到 B”。
- 不能补出口径，改为“改善了XX问题”或列为待确认。

### 不能直接写

- “精通某技术”，但经历里没有使用证据。
- “主导战略”，但只是学生项目或实习执行。
- “0-1搭建体系”，但原文只是整理表格或参与执行。
- “服务百万用户”，但原文无数据来源。
- JD 里出现但用户材料里没有的技术。

## 事实到简历的转换

每条事实进入简历前问 4 个问题：

1. 这个事实对目标 JD 有用吗？
2. 这个事实有没有证据来源？
3. 这个事实写强一点会不会面试解释不了？
4. 这个事实放在哪个模块最合适？

## 事实与岗位能力证据卡的关系

“能力证据卡”字段把事实关联到岗位能力证据卡（见 `capability-evidence-cards.md`）：

- 一张岗位能力证据卡由多条事实组成，覆盖情境、任务、动作、结果，以及它证明的通用能力和岗位专业能力。
- 岗位能力证据卡只能引用“已确认”事实。“待验证”事实进卡前必须先追问确认。
- 强 bullet、事实、岗位能力证据卡靠可读标题串联。追问预演答不上来时，顺着引用定位需要降级的 bullet。

## 处理顾问建议

顾问建议通常是“方向”，不是“事实”。

例子：

```text
顾问建议：这段经历可以往数据分析方向包装。
```

不能直接写：

```text
负责数据分析体系搭建。
```

应该先找事实：

```text
原文有：使用 Excel 统计活动报名和转化情况。
```

可写为：

```text
用 Excel 汇总活动报名、到课和转化数据，协助复盘不同渠道的报名质量。
```

## 输出给用户时怎么展示

不要把完整 JSON 都甩给用户。可以简化为：

```text
我能直接使用的事实：
- 你做过 XXX 项目，用到 Python / Pandas。
- 你参与过 XXX 活动复盘，有报名和转化数据。

需要确认的点：
- “效率提升50%”缺少计算口径，建议补一下原始耗时和优化后耗时。
- “主导”这个词偏强，除非你确实负责决策和最终结果，否则建议降级。
```
