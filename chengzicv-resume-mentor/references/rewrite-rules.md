# 模块改写规则

## 基本信息与求职状态

简历头部信息直接决定 HR 把候选人归到哪个筛选池。必须写清楚：

### 必写信息

- 姓名、手机、邮箱。
- 求职意向：最好只写一到两个，或者是xx行业，xx方向相关，岗位要求的底层能力模型必须大差不差，否则HR 会认为候选人不清楚自己要什么，影响意向度和稳定性。
- 毕业届次或工作年限：这是 HR 判断"应届/实习/社招"的第一依据。

### 毕业时间规则

教育背景里必须写 `起始年月 - 毕业年月`，不要只写入学年份。

同时在头部用一个短标签标明身份：

| 情况              | 标签写法         | HR 理解      |
| --------------- | ------------ | ---------- |
| 还没毕业，毕业时间在 1 年内 | 2027届 · 本科在读 | 可按应届生招聘流程走 |
| 已毕业不超过 2 年      | 应届生 / 2026届  | 应届生身份，可走校招 |
| 毕业 1-3 年        | 1年经验 / 2年经验  | 社招初级岗      |
| 毕业 3 年以上        | X年经验         | 社招         |

如果材料里没有毕业时间，列为待确认，不要猜。这个信息写错会直接导致简历被分到错误的筛选池。

### 求职状态（可选但推荐）

如果用户当前未在职或即将离职，可以加一句：

```text
未在职，目前正在找工作，周内到岗/随时到岗
```

这让 HR 知道候选人可以快速到岗，减少沟通成本。在职但看机会的可以写：

```text
在职，考虑新机会
```

不确定时不写，不要编。

### 求职意向数量控制

- 1 个方向最佳：简历所有内容聚焦一个岗位。
- 2-3 个方向可接受：但必须是相近方向，如"产品经理/项目管理"。
- 超过 3 个：必须提醒用户拆成多版简历，每版聚焦 1-2 个方向。

## 总体写法

每段经历尽量写成：

```text
在【特定业务场景】下，针对【具体问题】，通过【动作/工具/流程】，达成【可验证结果/交付物】。
```

不一定每条都完整五要素，但至少要有：

- 场景
- 动作
- 工具或方法
- 结果或交付物

## 方法论使用边界

可以把目标岗位常见方法论写成“具体动作”，但不能把它写成用户已经做过的事实，除非原文或用户确认过。

可参考的方法论：

- 产品：5Why、用户画像、需求优先级排序、竞品对比、PRD、原型走查。
- 运营：转化漏斗、内容复盘、活动拆解、渠道对比、用户分层。
- 数据：指标拆解、漏斗分析、异常值排查、SQL 查询、Excel 透视表。
- 职能：Excel 台账、流程梳理、SOP 检查表、OKR 拆解、资料清单。

错误：

```text
用户原文只说“做过活动”，就写“通过转化漏斗模型主导用户增长策略”。
```

正确：

```text
如果原文有报名、到课、转化数据，可以写“按报名、到课和转化三个环节整理活动数据，协助复盘不同渠道的报名质量”。
```

方法论要藏在动作里，不要只写名词。

## 动词强度

根据身份控制动词：

| 身份 | 推荐动词 | 谨慎使用 |
| --- | --- | --- |
| 应届 / 学生 | 参与、协助、支持、完成、整理、分析、跟进 | 负责、主导、牵头 |
| 实习 / 初级 | 参与、承担、跟进、落地、维护、优化 | 主导、制定战略 |
| 1-3年 | 负责、承担、推进、优化、搭建 | 战略、体系化主导 |
| 3年以上 | 负责、主导、设计、推动、搭建 | 仍需证据支持 |

如果原文没有证明决策权，不要把执行动作写成战略动作。

## 小标题规则

工作、实习、项目和校园经历中的每条职责 bullet 必须使用：

```text
- **小标题**：正文
```

小标题是 6-10 秒扫读时的定位锚点，不是可选装饰。只有把整段经历压缩为一行概述、不再使用职责 bullet 时可以省略。

要求：

- 通常为 4-8 个汉字或相近视觉长度；`Agent 工具系统`、`Prompt Cache 优化` 等中英混合标题可适当放宽。
- 名词感收尾。
- 优先用业务对象、功能模块、问题类型或结果命名。
- 技术词可以保留，但标题要让非本方向读者大致知道这块在解决什么。
- 正文保留可辩护的实现细节，不要因为补了小标题就把技术动作改成泛化总结。
- 每条只设一个主标题，不在正文里继续堆多个“标题：内容”。

正例：

- AI视频质量评估
- 素材生产链路
- 用户反馈复盘
- 数据看板搭建
- 报修流程梳理
- 接口联调排查
- Agent 工具系统
- 权限与文件安全
- 上下文与记忆
- Prompt Cache 优化

反例：

- Caption过滤机制优化
- 提利用率
- 建评估标准
- 数据驱动增长
- 赋能业务闭环
- 核心能力
- 系统优化

技术项目还要控制信息密度：

- 保留批切片、串行回退、校验条件、缓存边界等能区分方案的细节，前提是材料明确且面试可解释。
- 使用完整句子和分号组织“动作—机制—结果”，不要连续堆叠 `/`、`+`、`→`。
- 一条 bullet 承载一个主模块；同一模块内超过 3 个独立动作时，优先删弱信息或拆成两条。

## 工作经历

工作经历不要机械写成项目经历。重点写：

- 业务场景
- 日常工作对象
- 具体动作
- 协作对象
- 交付物
- 结果

结构建议：

```text
公司 | 岗位 | 时间
**项目背景**：1-2 句说明公司业务环境和这个岗位要解决的问题。让 HR 3 秒理解上下文。
**我的职责**：
- **业务对象**：针对什么业务/用户/流程，做了什么具体动作，交付了什么。
- **流程协作**：和谁对需求、怎么跟进、怎么处理问题。
- **数据复盘**：用什么工具统计什么指标，发现什么问题，支持什么调整。
**成果**：1-2 句总结这段经历最核心的交付物和结果。没数据写交付物，不编。
```

项目背景写法要求：

- 只写公司业务场景和这个岗位要解决的问题，不写虚大愿景。
- 1-2 句，不超过 50 字。
- 不要用"致力于"、"旨在"、"打造"这类虚词开头。
- 要让完全不了解这家公司的 HR 也能看懂。

成果行写法要求：

- 只写已完成的真实结果，不写进行中的承诺。
- 有数据写数据，没数据写交付物和覆盖范围。
- 不能只写"显著提升 XXX"这种无口径表达。

示例：

```text
**项目背景**：公司面向海外中型 ToB 客户提供软件服务，需要高效完成报价、合同、账单和回款等商务执行工作。
...（职责 bullets）
**成果**：账单 0 差错交付；合同核对覆盖全部经手合同；30+ 客户回款按节点推进；形成可交接的商务执行文档。
```

不要写：

```text
负责日常运营工作，提升用户活跃度，促进业务增长。
```

改成：

```text
- **社群活动复盘**：整理每周社群活动报名、到课和转化数据，用 Excel 对比不同主题的参与情况，协助调整后续活动选题。
```

## 项目经历

项目经历重点写：

- 为什么做这个项目。
- 项目解决什么问题。
- 用户本人做了哪一块。
- 用了什么技术/工具/方法。
- 结果是什么。

技术导向项目可以加：

```text
**技术栈**：React / Spring Boot / MongoDB
```

但只能写原文出现或用户确认的技术。不要为了 JD 匹配乱补技术名词。

推荐结构：

```text
项目名 | 角色 | 时间
**项目背景**：说明为什么做，不要写虚大愿景。
**技术栈**：只列真实技术。
**我的职责**：
- **小标题**：具体动作 + 工具/技术 + 结果/交付物。
**成果**：只写真实结果。没有数据就写交付物。
```

## 教育背景

教育背景主要服务于 HR 快速判断含金量。

可写内容：

- 学校、专业、学历、时间。
- 绩点、排名、奖学金。
- 与 JD 相关课程 3-6 门。
- 竞赛、论文、科研、证书。

院校标签要谨慎：

- 只有材料明确或可确认时才写 985、211、双一流、QS。
- 不确定不写。
- 不要用“大学/学院”粗暴判断一本二本。

格式示例：

```text
学校 | 学历 - 专业 | 时间
- **主修课程**：数据结构、数据库系统、机器学习、软件工程
- **成绩奖项**：GPA 3.7/4.0，获得校级二等奖学金
```

## 专业技能

技能不要写成“工具清单 + 熟练程度”。

写法：

```text
- **能力域**：工具名，能用它完成什么任务。
```

正例：

```text
- **数据分析**：SQL / Excel，可完成用户行为数据提取、转化漏斗统计和基础复盘。
- **产品设计**：Axure / 墨刀，可独立绘制低保真原型，并整理基础 PRD。
```

反例：

```text
- SQL（熟练）
- Excel（精通）
- 熟练掌握数据分析能力
```

技能证据规则：

- 经历中用过的技能可以前置。
- 材料只写“了解”的技能，不要写“熟练”。
- 没证据但用户可能会，可以列为追问，不直接写。
- 禁止使用“精通”，除非用户是多年专家且有强证据。

## 个人优势 / 自我评价

个人优势不是人格评价。不要写“沟通能力强、责任心强、学习能力强”。

写事实型优势：

```text
- **领域标签**：事实说明 + 结果。
```

标签类型：

- 领域经验：RAG问答系统开发、自媒体内容增长、B端客户沟通。
- 问题解决：智能客服系统优化、用户留存复盘、报修流程梳理。
- 工具能力：Python / Pandas数据处理、SQL数据分析、Figma原型设计。

示例：

```text
- **RAG知识库问答系统开发**：参与搭建基于 Qwen2.5 的知识库问答系统，配合完成混合检索和重排序调试，人工评测准确率从 65% 提升至 85%。

- **SQL / Excel数据分析**：可完成用户行为数据提取、运营指标统计和异常数据核对，支持活动复盘和渠道效果对比。
```

禁用表达：

- 能力强
- 思维好
- 经验丰富
- 扎实
- 优秀
- 良好
- 结果导向
- 问题导向
- 数据驱动
- 商业敏感度
- 企业级
- 工业级
- 全链路
- 端到端
- 赋能
- 闭环

注意：技术领域里的“系统”不一定是 AI 味，比如“推荐系统、客服系统、订单系统”可以保留。

## 完整简历结构

默认中文简历结构：

```text
姓名
电话 | 邮箱 | 城市 | 作品/个人主页（可选）
期望岗位：xxx

个人优势
教育背景
工作/实习经历
项目经历
专业技能
竞赛/证书/其他经历（可选）
```

如果是应届生：

- 教育背景可放前。
- 项目和实习比自我评价更重要。
- 校园经历只保留和目标岗位相关的。

如果是有工作经验：

- 工作经历优先。
- 教育背景压缩。
- 项目经历只保留代表性项目。

## 原文对照

用户需要审稿或你认为风险较高时，输出：

```text
【原文】
...

【优化后】
...

【为什么这么改】
- 补了业务场景
- 降低了动词强度
- 保留了真实工具
- 删除了无口径数据
```

交付最终版时不一定全部展示原文对照，但内部必须保留这个意识。

## 标点和句式

- 尽量不用分号。
- 不用双引号包装关键词。
- 不要连续堆四字词。
- 一条 bullet 里只讲一个主动作。
- 如果一句话太长，拆成两条。
