# 虚拟简历案例生成

当用户明确要求“虚拟案例、教学案例、示例简历、构造一份案例、按这条经历编一个样例”时，使用本路由。用户先描述岗位、经历主线或包装思路，Skill 再动态构造完整案例；不要在 reference 中写死行业和岗位。

## 模式判断

### 进入虚拟案例模式

用户明确表达以下任一意图：

- 为课程、产品、作品集或教学生成案例。
- 构造一位不存在的候选人。
- 根据一段经历设定生成示例简历。
- 展示某类岗位的包装和改写思路。
- 需要虚拟姓名、联系方式、公司和适量数据。

### 不进入虚拟案例模式

- 用户给出真实简历并要求直接投递。
- 用户要求把案例经历并入真实候选人名下。
- 用户没有说明是案例，且上下文明显指向真实求职。

无法判断时，只问一句：“这次是生成明确标注的虚拟教学案例，还是修改真实候选人的简历？”

## 输入理解

从用户描述中提取：

1. 目标岗位和职级。
2. 候选人的原始背景。
3. 经历时间线。
4. 希望重点展示的职责、项目或转型路径。
5. 需要体现的通用能力和岗位专业能力。
6. 用户明确指定的行业、工具、流程和结果方向。
7. 需要删除、压缩或弱化的内容。

用户描述已经足够形成主线时直接生成，不为虚构细节逐项追问。缺失内容按“初级、克制、可解释”的默认值补齐。

## 虚拟身份规则

虚拟案例不得使用真实个人联系方式。默认：

```text
姓名：橙子
电话：136-0000-0000
邮箱：chengzi@example.com
城市：按岗位场景选择常见城市，或写“目标城市”
性别：简历默认不写；教学目标确有需要时可随机设置
学校：某理工大学 / 某财经大学 / 某职业技术学院
公司：某教育科技公司 / 某互联网公司 / 某制造企业
```

规则：

- 姓名固定使用“橙子”；学校、公司可根据行业换成自然的泛化名称。
- 邮箱使用 `example.com`，避免生成真实邮箱。
- 电话使用带分隔符的示例号码，不生成可能联系到真实个人的完整号码。
- 不使用真实身份证号、详细住址、员工编号或可核验的私人信息。
- 文件名和文档标题必须包含“虚拟案例”。

## 经历构造规则

### 先形成统一主线

把用户描述重组为：

```text
候选人原始背景
→ 为什么进入当前经历
→ 做了哪些递进任务
→ 形成哪些交付物和小成果
→ 为什么匹配目标岗位
```

不要把每个点机械拆成互不相关的项目。优先合并同一公司、同一阶段或同一业务目标下的工作。

### 控制候选人层级

应届生、实习生和初级岗位优先使用：

- 参与、协助、承担、完成、整理、跟进、维护、优化。
- 小范围模块、具体流程、明确交付物。
- 主管或负责人承担最终决策。

除非用户明确要求高级岗位案例，否则不写：

- 主导公司战略。
- 从 0 到 1 搭建完整体系。
- 管理大型团队。
- 影响千万级用户。
- 极高增长率或行业领先成果。

### 动态补齐工作细节

可以根据用户给出的行业和岗位补齐：

- 业务场景和服务对象。
- 日常工作对象。
- 使用的工具、平台或方法。
- 与哪些角色协作。
- 一个合理难点和处理动作。
- 可展示的文档、表格、系统、代码、作品或流程。

补齐内容必须相互一致，不能一条写初级执行，另一条突然写战略负责人。

## 数据生成规则

虚拟案例可以生成数据，但要少、稳、前后一致。

### 数量控制

- 每段经历保留 1—3 个核心数字。
- 每条 bullet 最多放一个主要结果数字。
- 没必要量化的内容使用交付物、覆盖范围或完成状态。
- 优先使用绝对值、小区间和前后变化，不堆百分比。

### 量级原则

根据岗位和职级动态选择合理量级：

- 实习或初级招聘：可写参与 1—2 个岗位、完成若干次初筛、支持 1—2 人到岗。
- 初级运营：可写维护少量渠道、活动、内容或用户反馈，不写百万曝光。
- 初级技术：可写完成 1—3 个模块、处理若干典型问题、支持一次上线或内部使用。
- 职能岗位：可写维护台账、核对少量批次、整理 SOP 或降低少量重复工作。

这些只是量级参考，不要机械套数。以用户描述的业务规模为中心生成。

### 结果强度

优先选择“小但能证明做过”的结果：

- 支持 1—2 人实际到岗。
- 将单次重复操作缩短几分钟。
- 减少一部分手工复制、重复录入或遗漏。
- 完成一套评分表、知识库、SOP、看板或插件原型。
- 覆盖一个团队、一个岗位族或一次招聘周期。

避免：

- “效率提升 300%”。
- “招聘周期降低 80%”。
- “独立完成全部招聘决策”。
- 没有过程数据支撑的巨大业务成果。

### 数据一致性

存在漏斗、转化或前后变化时，先在内部建立简表再写简历：

```text
起点数据 → 中间环节 → 结果数据
```

例如招聘案例中，触达人数必须大于等于回复、初筛、推荐、面试、Offer 和到岗人数。Offer 接受与实际到岗分开。

## 包装规则

这里的包装包括：

- 按目标岗位重新排序经历。
- 将原始任务翻译成岗位能力。
- 合并重复内容，删除弱相关内容。
- 改写项目名称和小标题，让业务对象更清楚。
- 把工具清单写成具体动作和交付物。
- 用少量结果证明参与深度。

包装说明要回答：

1. 为什么保留这段经历。
2. 为什么把它放在这个位置。
3. 它证明哪项通用能力。
4. 它证明哪项岗位专业能力。
5. 哪些弱相关内容被压缩或删除。

## 默认交付

默认生成两个 Markdown 文件。

### 1. 虚拟案例完整版简历

文件名：

```text
虚拟案例-姓名-目标岗位-完整版简历.md
```

要求：

- 标题包含“虚拟案例”。
- 正文像一份完整、自然的中文简历。
- 不出现事实台账、设计说明、生成提示或风险标签。
- 求职意向最多两个相近方向。
- 使用虚拟身份和示例联系方式。
- 经历主线统一，数据克制且一致。

### 2. 虚拟案例设计说明

文件名：

```text
虚拟案例-姓名-目标岗位-案例设计说明.md
```

包含：

1. 用户原始设定摘要。
2. 简历定位和叙事主线。
3. 包装前后映射表。
4. 虚拟数据口径和一致性检查。
5. 岗位能力证据地图。
6. 为什么删除、合并或压缩某些内容。
7. 真实用户参考时应重新采集的字段。

用户明确要求作品集时，再增加：

```text
虚拟案例-姓名-目标岗位-作品集.md
```

## 写作要求

- 使用自然、具体、适合国内招聘平台的中文。
- 不写赋能、闭环、全链路、显著提升等空话。
- 每条经历尽量包含对象、动作、工具/方法和交付物/结果。
- 用小成果证明做过，不用大成果假装资深。
- 技术、业务和职能岗位都根据用户输入动态生成，不套固定技术招聘案例。
- 用户指定某种包装思路时，保留其核心方向，再修正时间线、角色边界和数据一致性。

## 质量检查

- 是否明确进入了虚拟案例模式？
- 文件名和标题是否包含“虚拟案例”？
- 是否使用了虚拟姓名、示例电话和 `example.com` 邮箱？
- 是否根据本轮用户描述动态生成，而非复用上一次案例？
- 是否只有少量、克制、互相一致的数据？
- 是否符合候选人的职级和职责边界？
- 是否同时交付成品简历与包装思路？
- 是否没有把案例内容写进真实用户简历？
